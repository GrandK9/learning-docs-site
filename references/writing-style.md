# 技术写作规范（专业严谨体）

本站与后续生成的站点统一采用本规范。目标是让文字读起来像内部技术文档，而不是公众号推文。

## 一、十条硬规则

| # | 规则 | 反例 | 正例 |
|---|------|------|------|
| 1 | **结论先行**：每节首句给判断，不铺垫 | 写 Skill 的人常犯三个错，且都不是"写得不够多" | 触发失败的原因有三类，均与文字量无关 |
| 2 | **量化替代形容**：能算就给数字 | 上下文开销明显变大了 | 单次回传从 1.2 MB 增至 9 MB，约 7.5 倍 |
| 3 | **陈述句为主**：无设问、反问、感叹 | 为什么它可以不叫 assets？ | 目录名由加载方式决定，与命名习惯无关 |
| 4 | **禁用口语比喻** | 技能就是废的 / 直接趴窝 / 白写 | 该技能无法被正确触发 / 进程持续满载 / 未产生实际作用 |
| 5 | **加粗克制**：只用于术语首次定义与硬约束 | 整段加粗 | 单句关键词加粗 |
| 6 | **第一人称用"本文"**：不用"我" | 我上一轮说错了 | 此前结论有误，已修正 |
| 7 | **标题名词化**：动宾或名词短语 | 别让技能白写 | 内容质量校验 |
| 8 | **段落 3~5 句**，单句不超过 60 字 | 长句套从句 | 一句一个判断 |
| 9 | **删除元评论**：不预告、不总结写作意图 | 这一章会讲三个问题 / 读完你能用自己的话答 | 直接陈述内容 |
| 10 | **术语保留原文**：不意译专有名词 | 渐进式披露原则 | progressive disclosure |

## 二、结构性要求

1. **每节不超过 3 层标题**（`##` → `###` → 无）。
2. **表格优先于并列句子**：三个以上同类信息一律表格化。
3. **代码块必需三件套**：说明一句、代码、出处 + 结论一句。
4. **不写"学习要点"式口号**，改为陈述该段落的结论。原写法 `**学习要点**：三层加载决定了什么该写进正文` 改为直接陈述，或删去。
5. **删去自测题的"先盖后看"等引导语**，折叠块标题写`参考答案 N`即可。

## 三、语气校准

| 场景 | 不写 | 改写 |
|------|------|------|
| 指出设计缺陷 | 这个设计挺离谱的 | 该设计在 X 场景下会导致 Y 后果 |
| 给出建议 | 建议你别这么干 | 不建议采用该方案，原因见下 |
| 承认错误 | 我之前说错了 | 此前结论不成立，实测数据如下 |
| 表达不确定 | 大概是这样 | 依据现有数据推断；未验证 |
| 描述规模 | 海量文件 | 19,217 个文件 |

## 四、保留项

以下内容不受本规范限制，保持原有形式：

- 官方原文引用（标注出处，不改写）。
- 实测数据表、日志片段、命令与输出。
- 章节末尾的 Official links。
- 自测题本身（问题可以口语化，答案是书面语）。
